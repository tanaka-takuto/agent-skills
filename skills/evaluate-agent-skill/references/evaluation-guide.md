# 比較の実施と記録

効果検証の設計、実行、既存記録の評価で必要な箇所だけ使う。実行回数や改善率の万能な合格値は置かず、用途、失敗の影響、予算から選ぶ。

## 比較条件と混入の防止

- 比較対象のSkill、参照資料、スクリプトの版と、モデル、実行ツール、常時指示、他のSkill、予算、検証器を記録する。更新前後で複数が変わった結果は、対象Skillだけの効果と断定しない。
- Skillなし条件では対象のパッケージを参照できない配置にし、同じ能力を別の指示から読み込んでいないか確認する。手順文だけを比べたい場合は道具を両条件に残し、その範囲を明記する。
- 発動の評価では、実際の一覧・description・選択機構を使い、近い非対象例も試す。明示的な呼出しで手順を読ませる比較は、発動精度の評価と分ける。
- 各条件を同じ元データ・版から複製し、新しい会話で開始する。先の解答、修正、評価結果を解答側へ渡さない。入力に必要な仕様や既存の決定は両条件へ同じように渡す。
- 外部応答、時刻、キャッシュなど結果を変える条件をそろえる。実サービスを使わない確認では、その境界を結果に残す。副作用のある操作は試験用の接続・データで隔離する。
- 比較に不要な正解や狙った不具合を実行者へ教えず、判定器と解答側の入力を分ける。繰返しの回数と順序を決め、途中で予算に達した結果も保存する。

## 判定方法と測る負担

成果の正しさと必須制約を先に判定し、負担との交換条件は利用者の目的と許容から判断する。説明が長いことや検査数が多いことを、そのまま品質と数えない。

| 観点         | 確認するもの                                                                                                                                 |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 成果         | 依頼に対応する成果物、実行結果、保存状態、失敗時の結果。テストは期待する利用結果を観測しているかも確認する。                                 |
| 範囲と制約   | 明示的な依頼を守ったか、非対象へ不要な工程や変更を追加していないか。                                                                         |
| 時間         | 開始から依頼された終了段階までの経過時間と、人が実際に使った時間を分ける。準備・指示・確認・修正を含め、並列作業の経過時間を単純加算しない。 |
| 費用         | 計測可能なトークンや利用費用、再試行と検証の費用。計測していない値は不明とする。                                                             |
| 判定の信頼性 | 既知の合格・不合格・境界例を正しく判定するか。モデル評価は基準例や人の判断で校正し、自己評価だけを証拠にしない。                             |

速度が目的なら品質と制約を満たした条件で比べ、品質改善が目的なら増えた負担も示す。最終成果に至っていない試行は、所要時間だけで成功扱いしない。

## 小さな比較記録

既存のログや成果物があれば再利用し、以下の情報を重複して書き直さない。必要な欄だけ使う。

| 項目     | 記録する内容                                                                         |
| -------- | ------------------------------------------------------------------------------------ |
| 評価範囲 | 補う不足、対象依頼、決めること、パッケージ全体か手順か、発動か実行か。               |
| 構成と版 | 比較元／候補、モデル・実行ツール・他の指示、入力の初期状態、予算、検証器。           |
| 事前基準 | 例ID、依頼、期待結果、必須制約、判定方法、負担の許容と根拠。                         |
| 各試行   | 例ID、条件、試行ID、成果物・ログ・検証結果の場所、時間・費用・人の負担、失敗や欠測。 |
| 判断     | 例ごとの差、反例、条件差、確認できた範囲、推奨、未検証、再評価する条件。             |

結果が揺れる場合は全試行の分布や件数を示す。難しい例の失敗を易しい例の成功で隠さず、重要な用途別にも比較する。検証した例が少ない場合は、その範囲の観察として述べる。測定条件が異なる記録は比較不能として分け、欠測を成功・無影響に置き換えない。

修正に使った例への適合だけを効果にしない。可能なら未使用の例でも確認し、予算や資料の制約でできなければ残る不確実性を示す。

## 根拠と適用判断

2026-11-20のAI駆動開発調査から、効果比較に必要な判断を抽出した。以下は資料の報告と、本Skillで採用した手順の対応であり、このSkill自体の効果を実証した結果ではない。

| 一次資料                                                                                                               | 報告・限界                                                                                                      | 適用した判断                                                 |
| ---------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| [SkillsBench v4](https://arxiv.org/html/2602.12670v4)                                                                  | 厳選した専門Skillで改善を報告。対象は再現可能なコンテナ内タスクで、実運用全体への一般化には限界がある。         | Skillなし／ありを同条件で比較し、構成別の効果を残す。        |
| [SWE-Skills-Bench v2](https://arxiv.org/html/2603.15401v2)                                                             | 公開開発Skillの効果は一様でなく、固定テンプレートが依頼を上書きする例も報告。要件の構成法や試行数に限界がある。 | 依頼と必須制約を基準にし、差未検出を無効性の証明と扱わない。 |
| [Evaluating AGENTS.md v2](https://arxiv.org/html/2602.11988v2)                                                         | 対象条件では指示が守られても、成功率の改善を伴わず負担が増える。Python中心の評価である。                        | 指示への従順さと成果を分け、追加負担も測る。                 |
| [Anthropic: Harness design for long-running apps](https://www.anthropic.com/research/harness-design-long-running-apps) | 評価器の調整と構成要素の除去比較を報告した当事者事例。                                                          | 判定器の校正と、必要な場合の要素別比較を使う。               |

特定のモデル、構成、数値を共通の既定値にしない。外部研究での改善を、今回の対象Skillの改善実績として転用しない。

## 例題による点検

2026-11-20に、作成者の会話・狙った結論を渡さず、別エージェントが本Skillと架空の比較記録を読んで4依頼を処理した。以下は既存記録の評価と計画作成の点検であり、対象Skillなし／ありの実験や、人間の判断負担の改善を測ったものではない。

| 架空の依頼・記録                                                   | 観察された判断                                                                                |
| ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| 推敲が42秒から20秒になるが、「結果不明なら再送しない」を逆転させる | 必須条件の回帰を速度で相殺せず導入を見送り、版と発動精度の未確認も示した。                    |
| 成功数が4/6から6/6になるが、モデルと道具も同時に変わる             | Skillだけの効果を判定できず、成果物がないため合格判定も未確認とした。                         |
| 同条件の2例で修正要求が減り、応答時間も短くなる                    | その2例の応答への限定的な改善とし、作業完了までの時間、実状態、費用、予算単位は未確認とした。 |
| 本番通知Skillを、送信・有料実行の権限なしで評価する                | 実行を始めず模擬接続の比較計画を作り、実配送と自動発動は別の未検証事項とした。                |

Skill導入による性能差、利用ホストでの自動発動、人間が読む際の有効性は、この点検では確かめていない。
