# レガシー移行のレビュー

必要な領域だけ読み、現状の証拠と移行中の状態に適用する。固定の方式や全項目の書類作成を要求しない。各項目を確認済み、未確認、理由付き対象外に分け、影響が大きい不足から解消する。

## 互換性と現状調査

- 「機能が同じ」を利用者、呼び出し元、条件、入力、出力、状態、副作用で記述する。内部のクラス構造やテーブル構造は、それ自体を外部が契約として利用していない限り一致の基準にしない。
- 見た目、操作順、URL、戻る操作、入力保持、エラー表示、APIのステータス・項目・型・順序、CSV・帳票の列や書式のどこを維持するかを明示する。「画面を改善する」ことも無断で機能維持に含めない。
- API・DBを直接読む外部システム、バッチ、月末・年度末処理、管理画面、手動SQL、Excel加工、ファイル交換、ストアドプロシージャ、トリガー、設定・機能フラグを探す。
- 同じ操作でも、権限、テナント、履歴、時刻、設定、データの世代で変わる挙動を探す。稼働結果、コード上可能な結果、期待仕様を分ける。
- 不具合に見える挙動も利用者が依存している可能性を調べる。欠陥を見つけたら影響と選択肢を示し、機能維持とは別の変更として扱う。脆弱性を無検討で互換契約に取り込まない。
- 全体の概略と依存を先に把握し、切り出す単位ごとに詳細化する。全仕様の復元が終わるまで何も進めない方式を避ける一方、未調査の範囲を移行済みに数えない。

## 方式と設計

| 方式                                                              | 適する条件                                               | 確かめる負担・弱点                                               |
| ----------------------------------------------------------------- | -------------------------------------------------------- | ---------------------------------------------------------------- |
| 一括切替                                                          | 対象が小さい、期限が厳しい、中断を許容できる、分割が困難 | 検証、データ転送、凍結、復旧が許容時間に収まるか                 |
| 機能ごとの段階置換（Strangler Fig）                               | 入口を振り分けられ、旧系と共存できる                     | 共有データ、跨る処理、振分層の障害・負荷、共存費用               |
| 抽象の背後で実装を置換（Branch by Abstraction）                   | 同一アプリ内の部品や依存ライブラリを置換する             | すべての呼出しを境界へ集められるか、長期の二重実装               |
| 契約を拡張して利用者を移し旧契約を縮退（Expand–Migrate–Contract） | API、スキーマ、イベントに新旧の利用者がいる              | 旧クライアント、遅延ジョブ、長時間トランザクションを含む移行完了 |

- 方式は組み合わせられる。切り出しのために分散サービス化する必然はなく、責務を分けた単一アプリも候補にする。
- 利用者の仕事を最後まで成立させる単位で移す。画面だけ移して裏のバッチ・認可・帳票を落とす、テーブルだけ分けて一つの取引の原子性を失う、といった分割を点検する。
- 必要なら変換層（Anti-corruption Layer）で旧契約と新モデルの意味を対応させる。変換層へ新しい業務ロジックを集めず、遅延、エラー、観測と撤去・恒久化の判断を持つ。
- 暫定構成と完成形を区別する。コピー、共有DB、代理呼出し、フラグが恒久化するなら理由と所有者を残す。

## 共存とデータ

- 機能・データの単位ごとに更新所有者と正本を指定する。同じ利用者や取引が新旧を行き来して一貫性が崩れるなら、機能・テナント・集約などの安定した単位で経路を固定する。
- 同期には、一方向・双方向、欠落、遅延、順序、重複、削除、競合、再開位置と修復方法を持たせる。単純な二重書きだけで原子的な更新や exactly-once を保証しない。
- DB更新と通知を連動させる場合、同一トランザクションに保存するOutboxと配送、CDCなどを条件に応じて比較する。受信側の冪等性と照合を設計し、Outboxだけで二つのDBが同期トランザクションになるとは考えない。
- 初期コピーの一貫した時点と変更ログの開始位置を対応させる。コピー中の更新・削除、ログ保持期間、処理遅延、再起動、バックフィルが新しい値を上書きする競合を検証する。
- 変換は版管理し、小分け、進捗記録、再実行、再開、負荷制御、失敗隔離を可能にする。復元可能な元データを残し、不正データを黙って削除・丸め・補完しない。
- IDの対応、採番・シーケンス、外部キー、NULLと空文字、文字コード・照合、日時・タイムゾーン、精度・丸め、既定値、論理削除、履歴、添付ファイルとオブジェクト参照を点検する。
- DBエンジンを変える場合、SQL構文の変換だけでなく比較・集計・並べ替え、分離レベル、ロック、トランザクション中の読み取り、制約、ストアド処理の意味を確かめる。
- 認証移行はID・権限・テナント境界・セッション・パスワード方式・SSOの対応を扱う。既存の権限を広げない。移行データと検証ログも必要な保護、保管と削除に含める。

## 検証と判定

- 特性テストで現行の実際の挙動を記録し、既存仕様、利用者の例と突き合わせる。新旧の一致と、正しい仕様への適合は別々の主張として扱う。
- 単発応答だけでなく操作の履歴を比較する。入力→保存→再読込、再送、タイムアウト後の成功、並行更新、取消、権限拒否などで状態と副作用を確認する。
- シャドー実行は読み取りまたは隔離された状態で行う。決済、メール、Webhook、実ファイルの更新を比較目的で二度実行しない。再送も個人情報、外部呼出し、負荷を含めて条件を整える。
- 同じ状態・時刻・設定で比べる。比較対象を同一実装同士で実行するなどして環境由来の揺らぎを確認し、時刻やIDなどの許可した差分だけを正規化する。並び順が契約ならソートして隠さない。
- データ件数に加え、キー集合、値と変換後の意味、参照関係、集計・残高などの不変条件を比べる。同期中の比較には共通の時点・水位を設ける。検証ツールの対象外を未確認として残す。
- データ移行ツールの成功はアプリの互換性を保証しない。画面、API、権限、バッチ、帳票、外部連携を対象範囲に沿って試験する。
- 希少な重要例、月末・年度末、長時間のジョブ、大量データ、キャッシュの温冷、インデックス、タイムアウト、運用監視を点検する。平均時間だけでなく必要な分布とピーク条件を見る。
- 判定条件は事前に決める。重大な契約違反を平均一致率で埋めず、未解決差分、観察漏れ、検証ツールの失敗、除外数を別に報告する。根拠なしに一致率・遅延・観察期間の合格値を設定しない。

## 切替・復旧・廃止

- リハーサルで転送時間、差分追従、照合時間、停止・再開、更新の引継ぎ、故障時の動作を実測する。負荷を掛ける比較・同期処理自体も計測する。
- 切替は新規受付、進行中リクエスト、トランザクション、キュー、スケジューラ、再試行と遅延コールバックを扱う。単にHTTP経路を変えて二重実行や取りこぼしを残さない。
- 新形式を書き始める前に必要な読取側へ互換性を準備する。古いアプリ、ジョブ、クライアントが残っていないことを確かめてから旧形式・列・APIを除く。
- 切り戻し可能なのは、旧系が切替後の更新を扱える場合に限る。逆同期、逆変換、再反映が必要なら実データに相当する例で試験する。情報が失われる変換の不可逆点を明示する。
- バックアップは取得だけでなく復元を試す。切替前のバックアップに戻すと受け付け済み更新が失われる場合、単純な復元を無損失の切り戻しと呼ばない。
- 段階ごとに責任者、監視項目、進行・停止条件、切り戻しの期限、前進修復、連絡と当番の引継ぎを用意する。新系のエラーだけでなく業務件数、差分と残存旧系アクセスを見る。
- 旧系廃止には、機能の移行、低頻度処理、残る利用者・依存、キューと保留取引、運用の引継ぎ、必要な履歴・証跡の保持を確認する。新系の稼働開始だけで終了としない。
- 一時的な同期・代理層・フラグ、旧ジョブ・接続・権限・秘密情報、不要な監視と費用を撤去する。外部向け互換APIを残すなら恒久運用の所有者を持つ。
- 移行中の現行変更は担当と版を追跡し、互換契約、新設計、データ対応と検証例へ取り込む。新系の設計と現行開発が別々の仕様へ進む状態を防ぐ。

## 記録の最小形

必要なものを既存の記録へ統合し、不要な表を増やさない。

| 記録           | 最小の項目                                                                               |
| -------------- | ---------------------------------------------------------------------------------------- |
| 互換契約と追跡 | 機能、呼出し元、条件、結果・状態・副作用、維持/変更/判断待ち、現行の根拠、新設計、検証例 |
| データ対応     | 元の意味、先の意味、変換、ID・履歴、例外の扱い、照合と修復、逆変換の限界                 |
| 段階の状態     | 入口、提供範囲、読取元、更新所有者、正本、同期方向、進行中の仕事、撤去対象               |
| 進行と復旧     | 開始・完了・停止の条件、担当、証拠、失敗時の処置、受け付け済み更新の扱い、不可逆点       |
| 判定と未確認   | 検証対象・版・母集団、一致・差分・除外、未検証の領域、影響、次の確認方法                 |

## 根拠となる一次資料

2026-10-10に調査。以下は判断の根拠であり、特定の製品や方式を必須にするものではない。製品の機能・制約や標準に依存する実装では、その時点の公式資料を確認する。

- [Michael Feathers: Characterization Testing](https://michaelfeathers.silvrback.com/characterization-testing) — 実際の挙動の記録と、利用者が依存する挙動の発見。
- [Patterns of Legacy Displacement](https://martinfowler.com/articles/patterns-legacy-displacement/) — 業務と技術の依存、薄い単位での置換、移行中の現行変更、暫定構成。
- [Microsoft: Strangler Fig](https://learn.microsoft.com/en-us/azure/architecture/patterns/strangler-fig) — 段階置換、共存の制約、入口と共有資源。
- [Microsoft: Anti-corruption Layer](https://learn.microsoft.com/en-us/azure/architecture/patterns/anti-corruption-layer) — 新旧モデルの意味の変換と維持費用。
- [Martin Fowler: Branch by Abstraction](https://martinfowler.com/bliki/BranchByAbstraction.html) — 抽象を介した複数実装の共存と置換。
- [Danilo Sato: Parallel Change](https://martinfowler.com/bliki/ParallelChange.html) — 拡張、移行、縮退による契約の進化と旧方式撤去。
- [GitHub: Scientist](https://github.com/github/scientist) — 新旧比較、環境の揺らぎ、データを変える処理への制限。
- [Stripe: Online migrations at scale](https://stripe.com/blog/online-migrations) — 大規模なオンライン移行、バックフィル、読み書きの切替と照合の実例。
- [AWS: Transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html) — 二重書きの部分失敗、通知の重複・順序と冪等性。
- [Google Cloud: Database migration concepts, Part 2](https://docs.cloud.google.com/architecture/database-migration-concepts-principles-part-2) — 問合せ・取引の意味、切替と逆方向のデータ移行。
- [AWS DMS: Data validation](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Validating.html) — 行ごとの照合、追加負荷と検証の対象外。
- [Amazon Builders' Library: ロールバックの安全性](https://aws.amazon.com/jp/builders-library/ensuring-rollback-safety-during-deployments/) — 新旧の混在、読取側の準備とロールバックの検証。
