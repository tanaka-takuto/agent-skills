# レガシーシステムを移行する

利用者と連携先が頼る機能と結果を保ち、内部設計は目的と制約から選ぶ。既存機能をそのまま移す依頼では機能維持を既定にし、不具合修正、機能廃止、操作や契約の変更は明示的な変更として扱う。

## 共通Skillの組み合わせ

作業に必要なSkillを利用可能な一覧から名前で探し、一覧になければ下表の相対パスから読む。既に読んだ内容は再利用し、実行順は不確実性と対象に合わせる。利用できないSkillは明記し、読んだふりをせず、このSkillの手順で補う。

| 必要な判断                                       | 使用するSkill                                                   |
| ------------------------------------------------ | --------------------------------------------------------------- |
| 移行の目的、守る価値、許容する変更を明らかにする | [elicit-intent](../elicit-intent/SKILL.md)                      |
| 現状の挙動と暗黙の契約を証拠から復元する         | [reconstruct-behavior](../reconstruct-behavior/SKILL.md)        |
| 不足、矛盾、依存、未検証の前提を見つける         | [find-gaps](../find-gaps/SKILL.md)                              |
| 「同じ機能」の解釈を具体例で照合する             | [verify-understanding](../verify-understanding/SKILL.md)        |
| 移行方式と実装の代替案を選ぶ                     | [compare-options](../compare-options/SKILL.md)                  |
| 責務、境界、不変条件、更新所有者と契約を定める   | [define-boundaries](../define-boundaries/SKILL.md)              |
| 目標となるWebアプリ全般を設計する                | [design-web-app](../design-web-app/SKILL.md)（Webが対象の場合） |

## 進め方

1. 今回の依頼が調査、設計、実装、切替のどこまでかを読み取り、既存の合意、コード、仕様、運用、データへ当たる。移行対象、機能維持の範囲、設計変更の裁量、期限、中断や損失の許容、次の段階に必要な判断を整理する。既に委任された実装判断で作業を止めない。
2. `reconstruct-behavior` で対象全体の概略を作り、最初の移行単位を深く調べる。画面、API、バッチ、帳票、権限、連携、手作業を含む入口から、結果、状態と副作用までをたどる。資料不足を利用者への質問だけで埋めず、利用可能な実装、データと観察で確かめる。
3. 復元した挙動を「維持する契約」「明示的に許可された変更」「判断待ち」に分け、条件、根拠、検証例へ結びつける。UI、API、データ、性能、運用のどの水準で同等かを具体化する。観測されない機能を勝手に削除せず、現行の欠陥や危険な挙動も黙って仕様化・修正せず、その依存と扱いを明らかにする。
4. `define-boundaries` と `compare-options` で移行単位、目標設計、移行方式を選ぶ。機能の依存と不変条件から分け、レガシーのクラス、テーブル、サービス数をそのまま新設計に写さない。Webなら `design-web-app` を使い、目的、互換性契約、運用条件を渡す。段階移行やマイクロサービスを必須とせず、最小で成立する設計も比べる。
5. 目標設計に加えて `plan-transition` で途中の構成を設計する。各段階の入口、読み取り元、更新所有者、正本、同期、移行済みの境界、進行中の処理を示す。外部向けの互換契約と内部モデルを必要に応じて変換層で分け、一時的な仕組みには撤去条件と担当を持たせる。
6. データがある場合は、対応、変換、識別子、例外データ、履歴、削除、制約、添付物を扱う。初期コピーと継続更新の接続、再実行、バックフィルとの競合、照合、修復を設計する。二重書きは部分失敗、順序と回復まで具体化できる場合に限って採用する。
7. 実装が依頼範囲なら、移行単位ごとに互換契約と検証例を基に新実装、データ変換、必要な暫定層を作る。`verify-equivalence` で契約と検証例を新設計・実装へ対応させ、許可された範囲で検証と修正を繰り返す。新旧の応答だけでなく状態、権限、帳票と外部副作用を比べる。シャドー実行や再送では副作用を隔離し、除外や未解決の差分を一致に数えない。機能の同等性と性能、可用性、運用の成立を別々に確かめる。
8. 切替前に、書込み・処理の引継ぎ、差分解消、観測、停止条件、復旧と旧系廃止をリハーサルする。実装や経路の切り戻しだけで、新系に受け付けた更新が旧系へ戻るとは考えない。逆変換・再反映の可能範囲を示し、不可逆点以降は前進修復も用意する。移行中の現行変更は版、契約、検証例と計画へ反映する。
9. [移行レビュー](references/migration-review.md) の対象に関係する項目を点検し、`capture-decisions` で判断、例外、根拠、未解決事項を残す。依頼された範囲の作業を完了し、次の段階に進める状態と、追加の証拠が必要な箇所を区別して返す。

## 出力と完了

依頼の粒度に合わせ、維持する機能と互換契約、現状の証拠と未確認、目標設計と選定理由、段階ごとの責任・データ・復旧、検証結果または計画、次の作業をまとめる。機能→契約→新設計→検証の対応をたどれる形にする。未実施の試験を成功と扱わず、低頻度処理を含む残存依存と運用の引継ぎを確認してから旧系廃止を完了とする。
