# Webアプリケーションを設計する

今回の目的と制約を満たし、次の実装や検証へ進める設計と判断理由を作る。

## 共通Skill

必要な同名SkillのSKILL.mdを利用可能な一覧から読み、その指示を適用する。同じ会話と記録を共有し、必要な仕事だけ使う。固定順序や別エージェントの起動は要求しない。

| 目的と譲れない条件を知る     | [elicit-intent](../elicit-intent/SKILL.md)               |
| 不足と矛盾を見つける         | [find-gaps](../find-gaps/SKILL.md)                       |
| 期待する振る舞いを照合する   | [verify-understanding](../verify-understanding/SKILL.md) |
| 選択肢と代償を比較する       | [compare-options](../compare-options/SKILL.md)           |
| 責務と連携の契約を具体化する | [define-boundaries](../define-boundaries/SKILL.md)       |

## 進め方

1. 目的、今回の範囲、設計の粒度、次に進む段階を整理する。既存アプリでは関連するコード、仕様、構成、過去の決定を読み、現状と変更対象を分ける。要望と設計判断を分け、未確定の要望がすべて決まるまで設計を止めない。
2. 利用者、主要な操作と期待結果、品質と体験、重要な制約を設計の判断基準にする。「速い」「変更しやすい」は、条件と期待結果のある場面へ具体化する。本人が決める価値や許容値と、委任された技術判断を区別する。
3. 重要な判断から有力な代替案を比較し、責務、データと状態の所有者、信頼と整合性の境界、外部との契約を具体化する。好みの技術やパターンから結論を始めず、追加する部品や仕組みを目的と根拠へ結びつける。
4. ユーザーの操作から画面、通信、処理、保存、応答までをたどり、状態の変化と利用者に見える結果を示す。失敗、再試行、権限不足、同時操作、変更のうち重要な場面でも、期待結果と守るべき条件を説明する。構成、契約、データ、画面の説明が食い違えば修正する。
5. [Web設計の点検観点](references/web-design-review.md)を読み、今回に適用する観点を選んで不足と矛盾を点検する。全観点を一律に深掘りせず、判断を変える不確実性と後から直しにくい判断を優先して検証する。計画した検証を実施済みにしない。
6. 質問は本人の価値、重要な要望の不足、両立しない条件に絞る。既知の回答を聞き直さず、委任された可逆的な判断は根拠と前提を示して進める。情報不足で止まる箇所を明示し、独立して進められる箇所は進める。
7. 重要な判断に、採用または推奨する案、理由、不採用案とその理由、受け入れる代償、根拠と未検証の仮定、見直し条件を結びつけて記録する。暫定案やAIの推奨を本人の合意へ置き換えず、変更時は影響する設計と検証を更新する。

## 成果と完了条件

範囲と判断基準、構成と責務、主要な流れと契約、重要な選択理由、未解決事項と次の行動を、依頼の粒度に合わせて返す。明示的に依頼された領域を省略せず、主要な場面では画面とサーバー双方の状態を対応づける。表や図は関係や違いの説明に必要なものだけ使い、既存の記録先があればそこを更新する。

今回の範囲で、重要な期待結果と制約に対応する設計があり、説明間の矛盾がなく、次の段階に必要な判断が決定または基準を伴って委任されていれば、その段階へ進める状態とする。未検証の仮定、残るリスク、保留する判断には、確認方法、担当が分かる場合は担当、次の段階への影響を残す。

選択や次の段階を変える重大な不明点が残れば、成立条件を示す暫定設計とする。提案、合意、設計上の整合確認、試作や実測による検証を区別し、「全体が検証済み」「変更にも万全」と保証しない。単純な依頼に全体設計や大量の文書を要求しない。
