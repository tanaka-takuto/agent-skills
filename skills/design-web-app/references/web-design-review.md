# Web設計の点検観点

依頼の範囲に適用する観点を選び、確認済みの根拠、未確認、対象外の理由を残す。狭い変更では変更先と影響先を点検する。機能が不要であることと、必要性をまだ確認していないことを区別する。

## 観点

| 観点                 | 判断を変える問い                                                                                                                                                                                      |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 目的と制約           | 誰のどの行動や成果を改善するか。対象範囲、成功条件、費用、期限、チームの能力と維持できる負担は何か。既存の決定に何が制約されるか。                                                                    |
| 画面と体験           | 主要な利用の流れを完遂できるか。導線、画面遷移、入力と取消、空・読込・失敗・再実行の状態はどうなるか。端末、キーボードや支援技術で使えるか。好みや世界観をどの実物で照合するか。                      |
| フロントと配信       | サーバー、クライアント、URL、一時入力のどれが状態を持つか。更新後の表示や複数タブは整合するか。初期表示、検索への露出、対話性、端末と回線の条件から配信やレンダリング方式を選べるか。                 |
| ドメインと責務       | 用語、判断ルール、状態遷移、常に守るべき条件を誰が所有するか。同名でも別の概念を混同していないか。境界の分割で変更や理解を局所化できるか。                                                            |
| APIと処理            | 利用者は誰か。操作、入力と出力、エラー、認可、ページ分割、再試行、互換性をどう契約するか。同期処理と非同期処理の完了を何で判断するか。必要な場合は取消と進捗をどう扱うか。                            |
| データと整合性       | 正本、識別子、関連、制約、履歴、検索と更新経路は何か。トランザクション、競合、キャッシュ、遅延や重複で何を許せるか。保存期間、削除、移行と復元をどう扱うか。                                          |
| 認証・認可と信頼     | セッション、本人確認、権限、所有権、テナントの境界をどこで検証するか。ブラウザからの入力を信用せず、直接のAPI呼び出しでも許可を守れるか。重要なデータと処理への脅威、秘密やログへの漏出をどう扱うか。 |
| 外部連携と非同期処理 | 外部の契約、制限、遅延、停止、重複、順序の変化に耐えられるか。タイムアウト、再試行の上限、冪等性、部分成功、再処理を誰が持つか。採用した保証は相手の実際の仕様と一致するか。                          |
| 性能と信頼性         | 利用の規模、重要な遅延、許容する停止やデータ損失は何か。律速、障害の波及、容量制限はどこか。必要な水準に見合う構成か。数値は要望、推定、実測のどれか。                                                |
| 実行環境と運用       | 環境、配備単位、設定と秘密、監視と調査、費用、バックアップ、復旧、担当をどうするか。コードとスキーマのバージョンが混在しても移行できるか。ロールバックできない変更には前進復旧などの対応があるか。    |
| 検証と変更           | 主要ルールと契約をどこで確かめるか。変更が及ぶ部品、API、データ、利用者はどこか。独立して検証や配備ができるか。将来の想定には根拠があり、備える費用と変更時の費用が見合うか。                         |

## 横断してたどる場面

通常の成功例に加え、判断を変えるものを選ぶ。全場面を毎回要求しない。

- 更新直後に読込、リロード、戻る操作をした場合に、何が画面に出るか。
- 保存後に応答が届かず、再送した場合に、利用者とシステムが何を確定できるか。
- 同時編集、連打、複数タブ、重複や順序が逆のイベントで、守るべき条件が崩れないか。
- ログイン期限切れ、権限変更、別テナントの識別子、直接のAPI呼び出しをどう扱うか。
- 入力の失敗、外部障害、処理の部分成功を利用者へどう伝え、復帰できるか。
- 新旧クライアント、旧キャッシュ、旧処理と新スキーマが共存する場合に動作するか。
- 既存データの移行、復元、削除と、運用担当による調査や再処理を実行できるか。

各場面で「条件と操作 → 所有者と境界 → 処理と状態 → 利用者に見える結果 → 守るべき条件」を対応づける。性能や実際の使いやすさは追跡だけで実証できないため、分析で確認した範囲と実物・実測で確かめる範囲を分ける。

## 点検の深さ

今必要な振る舞いに不可欠な複雑さと、選んだ構成が増やす複雑さを分ける。分割、抽象化、非同期化、キャッシュなどを足すときは、解く問題、増える負担、小さな案では足りない根拠を示す。単純さだけで必須の品質や将来変更の根拠を無視しない。

長い設計書、すべての図、すべてのテストを完了条件にしない。次の段階で誤解や手戻りになる判断を、根拠と不確実性が分かる深さで具体化する。

## 参照した一次資料

必要な論点の根拠を確認するときに参照する。個々の資料の技術選択を、そのまま必須の構成へ置き換えない。

- [NASA: Design Solution Definition](https://www.nasa.gov/reference/4-4-design-solution-definition/): 代替案、反復、技術の成熟度、設計を具体化する深さ。
- [NASA: Decision Analysis](https://www.nasa.gov/reference/6-8-decision-analysis/): 判断基準、同じ条件での評価、不確実性と分析量。
- [SEI: Quality Attribute Workshop](https://www.sei.cmu.edu/library/quality-attribute-workshop-collection/): 品質を具体的な場面で定義し、優先する。
- [SEI: ATAM](https://www.sei.cmu.edu/library/atam-method-for-architecture-evaluation/): 品質のトレードオフと設計上のリスクを分析する。
- [Parnas: Decomposing Systems into Modules](https://www.cs.lafayette.edu/~gexia/cs301/resources/parnas.html): 変更される設計判断を隠蔽する責務の分割。
- [DORA: Loosely Coupled Teams](https://dora.dev/capabilities/loosely-coupled-teams/): 技術名より独立した変更、検証、配備という成果を評価する。
- [Google SRE: Simplicity](https://sre.google/sre-book/simplicity/): 問題に不可欠な複雑さと構成が増やす複雑さを分ける。
- [web.dev: Rendering on the Web](https://web.dev/articles/rendering-on-the-web): 性能、配信、対話性などに応じてレンダリング方式を比較する。
- [W3C: Understanding WCAG 2.2](https://www.w3.org/WAI/WCAG22/Understanding/): 知覚、操作、理解などのアクセシビリティを点検する。規定本体との違いに注意する。
- [OWASP: Threat Modeling](https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html): データの流れと信頼境界から脅威と対処を検討する。
- [AWS: Retry with Backoff](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/retry-backoff.html): 再試行、冪等性、負荷と待ち時間の代償を点検する。
- [Microsoft: Design Principles](https://learn.microsoft.com/en-us/azure/architecture/guide/design-principles/): 業務、障害、進化と運用を含む設計。
- [Michael Nygard: Documenting Architecture Decisions](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions): 背景、状態、判断と不利益を含む帰結を残す。
- [C4 model: Diagrams](https://c4model.com/diagrams): 読み手と判断に役立つ抽象度の図だけを使う。
