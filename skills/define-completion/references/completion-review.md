## 混同しやすいもの

| 種類                               | 何を表すか                             | 開発での扱い                                                                                       |
| ---------------------------------- | -------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 目的                               | 利用者や業務に起こしたい変化           | 条件を満たせば目的へ近づくかを点検する。長期的な売上や利用継続は、実装の合否だけでは実証できない。 |
| 機能の受け入れ条件                 | 今回の機能が成立する振る舞いと制約     | 条件、操作、結果を具体化し、必要な例と確認方法を結びつける。                                       |
| 共通品質基準（Definition of Done） | 成果を完了と呼ぶための共通の品質水準   | リポジトリやチームの採用済み基準を継承する。どの機能にも同じ長大な基準を新設しない。               |
| 作業計画                           | 結果へ至る手順や分担                   | 必須の手順でなければ実行者の裁量にする。「関数を追加する」だけでは機能の合格を示さない。           |
| 検証方法と証拠                     | 条件を満たしたか判定する手段と観測結果 | コマンド実行、終了コード、画面操作、再読込後の状態などを結果に対応させる。                         |
| goalの条件                         | 自律実行で目指す終点と判定の指示       | 対象、終了段階、必須条件と証拠を引き継ぐ。ホストの終了は、実際の成功と同じとは限らない。           |

Scrum GuideはDoDを成果の品質に関する共有基準として定義する。機能固有の規則と具体例を整理する部分にはCucumberのExample Mappingを使える。[Scrum Guide](https://scrumguides.org/scrum-guide.html#commitment-definition-of-done)、[Example Mapping](https://cucumber.io/docs/bdd/example-mapping/)

## よく起こる課題と対処

| 課題                                               | 失敗する理由                                     | 条件へ反映すること                                                                 |
| -------------------------------------------------- | ------------------------------------------------ | ---------------------------------------------------------------------------------- |
| 「適切に動く」「使いやすい」で終える               | 判定者によって合否が変わる                       | 実際の場面、期待する結果、比較対象や判断基準を示す。                               |
| Issue本文だけを転記する                            | 関連する決定、変更された条件、暗黙の依存を落とす | Issueの議論、採用済みの仕様、関連する指示を読み、矛盾と未確認を残す。              |
| 一項目に複数の要求をまとめる                       | 部分的に動く場合の未達箇所が分からない           | 独立した判断を分けてIDを付け、共通の前提はまとめる。                               |
| 実装手順を合格条件にする                           | 指定どおりのコードでも成果が成立しない           | 操作から結果までを条件にする。不可欠な実装制約だけ根拠とともに残す。               |
| 「テストが全部通る」だけにする                     | 試験のない機能や、試験が見ない挙動を取りこぼす   | 要求と試験の対応を確認し、実物で見る必要がある結果を補う。                         |
| APIやモックが成功したので画面も合格にする          | 接続、表示、保存、再読込のどこかが壊れ得る       | 利用者の操作から結果までたどり、必要なら新しい読込や別セッションで保存を確かめる。 |
| 件数、ファイル数、カバレッジだけで判定する         | 本来の価値を代理指標が十分に表していない         | 間違った出力や欠落でも合格できないかを考える。数値は必要な結果の補助にする。       |
| 後から合格値を作る                                 | 実装に都合のよい条件になりやすい                 | 根拠のある基準を結果の評価前に決め、未確認の値は提案と明示する。                   |
| 成功する例しかない                                 | 拒否、境界、再実行、回復の誤りを見逃す           | 結果を変える重要な不成立例も選ぶ。全組合せを無条件に要求しない。                   |
| 確認用コマンドやデータが存在しない                 | 良い条件でも実際には判定できない                 | 手段の存在、対象範囲、実行環境、権限を確認し、不足を検証の準備として残す。         |
| 未実施を完了報告で埋める                           | 主張と実際の最終状態が一致しない                 | 実行結果を求め、証拠不足には未確認という判定を許す。                               |
| すべての不具合を直す、完全に最適化する             | 対象が増え続け、有限の終点がない                 | 今回の要求、影響する契約、観測範囲と終了段階を限定する。                           |
| 利用者の承認や外部サービスの復旧を自動達成に含める | エージェントが自力で成立させられない             | 必要な依存と役割を残し、実行可能な段階へ分ける。全体が完了したとは扱わない。       |
| 合格するよう条件や試験を削る                       | 判定そのものを変えて未達を隠す                   | 条件の版と変更理由を残す。正当な仕様変更や試験追加と、無断の緩和を区別する。       |

明確さ、単一の判断、追跡可能性、検証可能性はNASAの要件チェックを参考にした。AIの早すぎる完了報告と画面まで届かない試験はAnthropicの実験で報告されている。代理指標を満たして目的を外す点はDeepMindの研究から得た注意であり、上表の開発への適用は本Skillの判断である。[NASA Appendix C](https://www.nasa.gov/reference/appendix-c-how-to-write-a-good-requirement/)、[長時間エージェントの実験](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)、[Specification gaming](https://deepmind.google/blog/specification-gaming-the-flip-side-of-ai-ingenuity/)

## 条件を作る流れ

1. **基準を読む。** 要求、背景、今回の範囲、採用済みの決定、共通品質基準を拾う。出典の状態と版を残し、「新しい記述だから優先」「コードがそうだから仕様」とは決めない。
2. **結果へ言い換える。** 各要求で何が変われば価値が出るか、何を守る必要があるかを抽出する。必須制約と参考目標を分ける。条件に不要な技術選定を加えない。
3. **例で具体化する。** 同じ規則の成功例、不成立例、境界例を置く。例から新しい規則が必要と分かったら、推測で確定せず未決として残す。
4. **証明方法を選ぶ。** 結果を観測できる最小の確認を選ぶ。コードの試験で足りる条件と、実物・実測・人の判断が必要な条件を分ける。
5. **双方向に点検する。** 各重要要求に条件と証拠があるか、各条件に正当な根拠があるかを見る。既存のIDや記録を使い、同じ情報を複数の文書へ複製しない。
6. **判定を試す。** 合格例と不合格例を同じ基準で評価する。条件を満たすだけの空実装、固定出力、モック、確認の省略で合格できるなら条件か証拠が弱い。妥当な別実装が落ちるなら条件が強すぎる。
7. **渡せる範囲を決める。** 重要な未決、確認の権限、外部依存、予算などの指定を引き継ぐ。独立して進められる段階があれば明示する。元の終了段階を変更するなら、その理由と決定状態を残す。

NASAは要求の必要性・実現性・過度な指定を確認し、要求を作る時点で検証方法と出典を対応させることを勧めている。ここでは小さなIssueにも使える最小の記録に縮める。[Technical Requirements Definition](https://www.nasa.gov/reference/4-2-technical-requirements-definition/)、[Verification Matrix](https://www.nasa.gov/reference/appendix-d-requirements-verification-matrix/)

## 条件と証拠の最小形

| 項目           | 残す内容                                                                                 |
| -------------- | ---------------------------------------------------------------------------------------- |
| IDと必須性     | 元のIDがあれば再利用する。必須条件と参考目標を区別する。                                 |
| 適用条件と操作 | 利用者、権限、初期状態、入力、順序など結果を変える条件。                                 |
| 期待結果       | 画面、応答、再読込後の情報、拒否、副作用などの合格結果。                                 |
| 根拠           | Issueの項目、採用済み仕様、決定への場所と必要な版。推測は分ける。                        |
| 判定方法       | 確認対象、実行環境、コマンドや操作、観測点、閾値があればその根拠。                       |
| 証拠           | 必要なログ、観測記録、成果物など。既存のCI結果や会話で足りれば新しい証拠文書を作らない。 |

数値条件には、単位、範囲、境界の包含、計測条件、許容差を必要な範囲で残す。性能なら平均値だけでよいか、分位点やピーク時が重要かを目的から選ぶ。根拠のない「1秒以内」「カバレッジ100%」「必ず3回試す」を既定にしない。

検証結果には確認したコード・成果物の版と環境を対応させる。後から関連する変更があれば影響する証拠を再確認する。実行前は検証計画であり、既存の成功ログが異なる版や環境ならそのまま流用しない。[Product Verification](https://www.nasa.gov/reference/5-3-product-verification/)

利用者の期待を実物で満たせるかの確認と、記述された仕様への適合確認を分ける。単に要件どおりに作れたことから事業上の成功を保証しない。[Product Validation](https://www.nasa.gov/reference/5-4-product-validation/)

## 書き換え例

以下は方法を示す架空の例である。ID、仕様、コマンド、許容値を実際の案件へ自動で持ち込まない。

### 保存機能

「保存機能を実装し、テストを追加する」では、何が保存されれば合格かがない。仕様で既に合意されている内容を次のように条件へ変える。

| ID    | 条件と期待結果                                                               | 確認と証拠                                                               |
| ----- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| AC-01 | 編集権限を持つ利用者が有効な名前を入力して保存すると、その名前が表示される。 | 対象版の実画面で操作し、画面結果を観測する。                             |
| AC-02 | AC-01で保存した後にページを新しく読み込むと、同じ名前が表示される。          | 再読込でサーバーから読む経路を確かめ、保存した値と表示結果を対応させる。 |
| AC-03 | 合意済みの無効入力ではエラー理由が表示され、以前の保存値が保たれる。         | 境界入力の試験と、失敗後の再読込結果を確認する。                         |
| AC-04 | 編集権限のない利用者が直接更新APIを呼んでも更新は拒否される。                | 認可の試験で拒否と保存値が変わらないことを確認する。                     |

AC-03の入力範囲、AC-04の権限やエラー契約が未定なら、ここをAIの推測で仕様化しない。再読込やAPIが存在しない対象では別の観測方法を選ぶ。

Given/When/Thenは前提、操作、結果を分ける書き方として役立つが、構文の採用やCucumberの導入は必須ではない。Cucumberの利用者向け例は観測可能な出力を重視する。内部状態の確認は、永続化や権限などの証拠として必要な場合に補う。[Gherkin Reference](https://cucumber.io/docs/gherkin/reference/)

### 不具合修正

「Issue #Nを解決する」を、Issueに記載された入力・環境で不具合が再現しなくなり、期待結果が成立する条件へ変える。回帰を防ぐ試験は、既存実装で問題を検出できることも確認する。影響する既存契約とリポジトリの必須チェックを対応させる。Issueを閉じた状態だけを修正の証拠にしない。

### 体験や性能が曖昧な改善

「一覧を速く使いやすくする」だけでは数値を作らない。対象操作、困っている場面、データ量、端末・回線、許容できる結果を確認する。未確認なら必要な調査・計測の段階の条件を提案し、機能改善全体の条件はgoal用の文章も含めて下書きに残す。終了段階を無断で変更しない。

見た目は合意済みの参考例、避けたい例、体験上の制約で照合する。点数化する場合は基準例と判断者を定める。AIの自己評価や高い総合点だけでは必須条件の不合格を埋めない。Anthropicの設計実験でも評価基準を具体化し、別の評価器を例で調整しているが、その構成や数値を必須にはしない。[Harness Design](https://www.anthropic.com/engineering/harness-design-long-running-apps)

## goalへの引継ぎ

引継ぎの本文は、特定のコマンドから独立して作る。ホストが決まっていれば現在の公式仕様に合わせる。未知の設定、予算、ツール名や権限を作らない。

```text
対象: <Issue/要求と、参照する基準資料の版・場所>
目的と今回の範囲: <望む変化、含む範囲、対象外、終了する段階>
達成条件: <必須条件を直接記すか、読める条件記録の版とIDを指定する>
確認: <条件ごとの確認方法、対象環境と観測点>
証拠: <実行した確認と結果、対象版、既存の証拠の場所を示す>
制約: <維持する契約、条件を無断で緩和しないこと、既存の実行権限>
未達時: <未達条件、証拠不足、外部確認待ちと次の行動を報告する>
終了制限: <指定されている場合だけ予算や期限を引き継ぎ、達成と区別する>
```

各行は必要なものだけ使う。短い依頼なら一段落で足りる。記録へ参照するだけで重要な制約や未決を隠さず、長い原文の再掲で条件を埋めない。

調査時点のClaude Code `/goal` は、条件と会話から別モデルが判定する。評価器が独立してコマンドを実行したりファイルを読んだりするわけではない。したがって、作業を行う側が試験の実行結果などを会話に示す指示が必要である。条件は4,000文字までで、goal自体は権限モードを変更しない。この仕様を他のホストへ一般化しない。[Claude Code goal](https://code.claude.com/docs/en/goal#write-an-effective-condition)

「条件を満たす」と「予算や時間が尽きて終了する」を区別する。ホストによって達成、不可能、エラー、停止の扱いは異なる。実行可能な実装段階のgoalと、外部承認・配備・実運用の確認が必要な全体の条件を分ける場合も、後者を達成済みにしない。

## 最後の点検

- 元の重要要求と採用済みの決定が、条件から追跡できるか。
- 各条件の合否を別の実行者と判定者が再現できるか。根拠のない追加や隠れた判定条件はないか。
- 成功例だけでなく、誤って成立してはいけない重要な例があるか。
- 結果を固定するだけの実装、モックだけの成功、状態の未保存で合格できないか。
- 妥当な別実装を、不要な手順・ファイル名・技術の指定で不合格にしていないか。
- 条件に適した確認手段があり、実行環境と権限がそろうか。存在しないコマンドを実行済みと扱っていないか。
- CI、スクリーンショット、自己申告が何を示し、何を示さないかを区別したか。
- 必須条件の一つの不合格を、平均点や参考目標の達成で埋めていないか。
- 条件の合意状態と、実際の検証状態を分けたか。条件作成、実装完了、検証完了を混同していないか。
- 未確認を許す判定があり、未実施や確認待ちを成功に数えないか。
- 判定する版と環境、元の条件の変更方法が分かるか。単にチェック欄が付いたことを証拠にしていないか。
- 依頼された終了段階が明確か。PR作成・マージ・配備・運用確認を無断で追加または除外していないか。

判定は可能なところを機械的にし、主観が残るところは例を伴う基準と人の判断を組み合わせる。AIによる判定も不確実であり、証拠不足のまま合格にしない。結果を変える確認に集中し、全ファイルの専用試験や大量の証拠資料を一律に要求しない。[Demystifying Evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

## 例題レビュー

作成時に、次の入力へ手順を手動で適用して、作る条件と判定を点検した。複数モデルや実アプリでの実行試験ではなく、Skill本文の例題レビューである。

| 入力と前提                                                                                     | 作る条件・残す事項                                                             | 点検した判定                                                                             |
| ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| 保存した名前が再読込で戻る。変更後の名前を保持する仕様が確定し、実装修正までを依頼されている。 | 保存後の新しい読込で入力値が表示される条件、回帰試験、対象版の確認結果。       | 保存直後の表示だけでは証拠不足。再読込で元に戻るなら不合格。PR作成や配備を追加しない。   |
| 「一覧を速くする」とだけあり、許容遅延、規模、端末が未定。                                     | 遅さが起きる操作を確認し、必要な計測を提案する。改善の閾値とgoal本文は下書き。 | 勝手な1秒以内という数値を採用しない。基準が未定のまま実行可能とは扱わない。              |
| プレビュー環境で動作確認してPRを作る依頼。デプロイに必要な権限がまだない。                     | ローカルの実装・検証、権限の確認待ち、プレビュー確認、PR作成を対応させる。     | ローカル成功だけで全体の完了にしない。権限不足を理由にプレビュー確認を条件から削らない。 |
| CLIが指定入力から正しいJSONを出す仕様で、パーサーの関数名やライブラリは委任されている。        | 入力と期待するJSONの意味、失敗時の契約、確認方法を条件にする。                 | 固定出力だけの実装は別入力で落ちる。期待結果が同じ別ライブラリの実装は合格にできる。     |
| Skillの文章だけを整形する依頼。機能や達成条件の変更は求められていない。                        | `define-completion` の発動対象に含めず、既存の整形手順を使う。                 | goalの新設や開発開始を付け足さない。                                                     |

曖昧な性能改善の例から、下書きという状態を説明文だけでなくgoal用の文章にも明示するよう本文を補強した。

## 一次資料

以下の12資料を参照した。推奨と必須規則、各資料の文脈と本Skillへの適用を区別する。

1. [NASA: How to Write a Good Requirement](https://www.nasa.gov/reference/appendix-c-how-to-write-a-good-requirement/) — 曖昧さ、単一の判断、必要性、検証可能性。
2. [NASA: Technical Requirements Definition](https://www.nasa.gov/reference/4-2-technical-requirements-definition/) — 意図への追跡、仮定、実現性、過度な指定、変更管理。
