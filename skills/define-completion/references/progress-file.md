# 完了条件・進捗ファイル

`define-completion` と `define-loop` で共用する記録の形式と更新規則。条件の作成者は記録と実行者への更新指示を用意し、対象作業の実行者が判定・証拠・進捗を更新する。記録の作成だけでは対象作業を開始しない。

## 保存先と構成

- 指定された保存先、次に同じ作業の既存の記録を優先する。既存の形式やファイル分割は保ち、Markdownへの移行や複製を一律に行わない。
- どちらもなければ、対象作業のルートに `completion/<task-id>.md` を作る。作業を識別できる安定したIDを使い、再開のたびに新しいファイルを作らない。Skillのインストール先や一時領域には置かない。
- 新規作成では1タスク1ファイルを基本にし、目的・範囲・基準資料・完了条件を、更新される判定・証拠・進捗と別の項目にする。`define-loop` は同じファイルに実行指示と実行状態を加える。
- 既存の条件ID、判定、証拠、未決事項、利用者の編集を保って必要な箇所だけ更新する。既存の仕様書を参照する場合は、その場所・版を残し、条件の本文を二重管理しない。
- 会話内だけの出力が指定された場合や、保存先を特定できない・書込みできない場合は、本文を会話に示して未保存の理由を残す。保存したと報告する前に読戻して内容を確認し、会話と引継ぎ本文に記録の場所を示す。

## チェックと判定

- `[x]` は、その条件に必要な検証を行い、対象の版・環境に有効な証拠があることを表す。条件の作成、実装の終了、作業計画の消化だけではチェックを付けない。
- 未着手、作業中、修正済み・未検証、不合格、確認待ち、検証不能は `[ ]` のまま短い状態説明を付ける。初期状態は未検証とし、既存の判定を一律に初期化しない。
- チェックを付ける更新には、対象の版・環境、確認方法、観測結果、証拠を含める。証拠は記録から解決できる場所への参照か、再判定に足りる短い観測記録にする。未コミット変更があれば、commitだけでなく差分も識別できる記録を残す。
- 条件、成果物、環境、データの変更で証拠が無効になった条件は、理由と以前の結果を残して未チェックへ戻す。再開しただけで全条件を失効させず、影響を照合して必要な範囲を再検証する。
- 進捗更新では条件の本文・必須区分・閾値を変えない。正当な変更は既存の権限と決定手順に従い、条件版、理由、影響する条件と再検証範囲を記録する。
- 必須条件、参考目標、不変条件を区別する。完了は同じ最終成果物について必須条件と不変条件の有効な証拠で判定し、チェック数や作業項目の消化率だけでは決めない。

## 途中保存と再開

実行指示へ、次の更新・再開手順を含める。完了条件だけを作る依頼では、ループの予算や運転規則まで追加する必要はない。

1. 開始時にこの記録を読み、作業場所・成果物・条件版・証拠・権限・残予算を実物と照合する。
2. 検証結果が出た時点、方針変更時、待機・停止時に、判定・証拠、試した方法と分かったこと、未解決事項、次の一手、停止理由を保存する。ループでは使用予算と残量も更新する。終了直前の一括保存だけに頼らない。
3. 外部変更の前には操作ID・対象・意図を保存する。中断やタイムアウトで結果が不明なら、再送する前に読戻し等で成立を照合する。
4. 再開時は最後の保存以降の変更や実行途中の操作も確認し、記録を補正する。古い「作業中」の表示だけで処理が動いていると判断せず、必要なら実行環境の状態を確認する。
5. 未達条件・依存・残予算から次の仕事を選ぶ。文脈やセッションが変わっても使用予算をリセットしない。条件が未確定、観測不能、外部待ちなら、その理由と再開に必要な変化を残す。

突然の中断では最後の保存以降が未記録になり得る。このファイルは再開の判断材料であり、自動起動、プロセスの復元、排他や予算の強制を実装するものではない。

## Markdownのひな形

完了条件だけなら「実行指示」「実行状態」「再開時の確認」は省略できる。条件の数や記録の量は作業に合わせ、該当しない欄は省く。既存の条件を参照する場合、チェック項目には条件ID・版・参照先と判定を置く。

```markdown
# <作業名>

- タスクID: <安定したID>
- 目的・範囲・対象外: <今回求める結果と境界>
- 完了段階: <実装・PR・配備等、今回終える段階>
- 基準資料: <場所・版・採用状態>
- 条件版: <v1等。進捗更新だけでは変えない>
- 記録の状態: <条件作成済み / 重大な未決がある下書き>
- 最終更新: <日時・タイムゾーン>

## 完了条件

- [ ] AC-01 必須: <適用条件・操作 → 観測可能な期待結果>
  - 根拠: <要求や決定への参照>
  - 確認方法: <手段・必要な環境やデータ>
  - 現在の状態: 未検証
  - 検証対象・確認日時: <成果物の版・環境・日時。未実施ならその旨>
  - 結果・証拠: <観測結果と証拠の場所。未取得ならその旨>

## 不変条件・参考目標

<必須条件と区別して列挙し、必要な判定・証拠を対応させる>

## 未決事項

<内容、影響する条件、確認方法・判断者。なければ「なし」>

## 実行指示

<define-loopで作る各回の処理、検証、続行・停止、権限・予算、復旧等>
開始時にこのファイルを読み、検証後に判定・証拠・次の一手を保存する。

## 実行状態

- 全体の状態: 未着手
- 作業場所・成果物: <リポジトリ、ブランチ、commitと未コミット差分等>
- 直前の作業・観測: <何をして、何が分かったか>
- 試した方法: <失敗・棄却した仮説と結果。次の判断に必要な分>
- 次の一手: <対象の条件IDと具体的な行動>
- 使用予算・残量: <上限、計測元、使用量、残量>
- 停止理由・再開契機: <なければ「なし」>
- 結果不明の操作: <操作ID・対象・意図・照合方法。なければ「なし」>

## 再開時の確認

1. 記録と実物、最後の保存以降の変更、結果不明の操作を照合する。
2. 証拠の有効性を確認し、影響する条件を再検証する。
3. 権限・依存・残予算を確認し、未達条件から次の仕事を選ぶ。
```
