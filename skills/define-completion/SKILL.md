# 完了条件を作る

何が成立し、何を確かめれば今回の作業を終えられるかを、別の実行者と判定者が再現できる形にする。条件の作成と、対象作業の実行・goalの開始を分ける。

## 共通Skill

必要なSkillだけ利用可能な一覧から探して読み、同じ会話と記録を使う。既に読んだ内容は再利用する。

| 必要な仕事                         | Skill                                                    |
| ---------------------------------- | -------------------------------------------------------- |
| 目的と譲れない条件を知る           | [elicit-intent](../elicit-intent/SKILL.md)               |
| 不足、矛盾、検証の抜けを見つける   | [find-gaps](../find-gaps/SKILL.md)                       |
| 合否が分かれる具体例を照合する     | [verify-understanding](../verify-understanding/SKILL.md) |
| 検証方法や成立条件の仮定を確かめる | [test-assumptions](../test-assumptions/SKILL.md)         |
| 条件、根拠、委任、未決を残す       | [capture-decisions](../capture-decisions/SKILL.md)       |

一覧になければ上表の相対パスを使う。見つからなければ依存不足を明示し、このSkillの手順で可能な整理を進める。読んでいないSkillの処理を実施済みとは扱わない。

## 進め方

1. 対象のIssueと関連する議論、依頼範囲、リポジトリ指示、採用済みの仕様・決定、既存の検証手段を読む。資料の場所、採用状態、版や確認時点を残す。実装や古いIssueの挙動だけを期待仕様にせず、資料間の優先順位が不明な矛盾は確認事項にする。
2. 望む変化、今回の対象と対象外、終了する段階を定める。機能固有の受け入れ条件、既存の共通品質基準、作業手順を区別する。実装、PR作成、マージ、配備、運用確認を一括で完了と扱わず、依頼された段階だけ条件に含める。既存の合意や委任を聞き直さない。
3. 要求ごとに、誰がどの条件で何をすると、どの観測可能な結果が成立するかを書く。通常例、境界、失敗・回復、権限、永続化、既存の契約のうち結果を変える場面を選ぶ。一つの条件に独立した判断を詰め込まず、関連条件にIDを付ける。実装方法は必須制約や採用済みの決定がある場合だけ固定する。
4. 各条件に、元の要求、判定方法、必要な証拠を対応させる。試験、実物の操作、検査、分析、人の判断を使い分け、確認する版・環境・データ・権限と観測点を必要な範囲で指定する。利用者に見える結果を優先し、保存状態や副作用も重要なら確認する。既存のコマンドは設定やスクリプトで存在と対象を確かめ、未作成の試験は予定と記す。
5. 「速い」「使いやすい」「既存機能を壊さない」を判定できる場面へ具体化する。性能は対象操作、負荷・端末などの条件、計測方法、閾値と根拠を組にする。体験は基準となる実物、合格・不合格例、判断者を使う。数値、対応端末、許容差、品質基準を捏造せず、未確認の提案は分ける。
6. 元の重要な要求から条件・証拠へたどり、逆向きにも根拠のない追加を点検する。「条件を満たすが目的を達成しない実装」と「目的を達成するのに落ちる実装」を考え、代理指標、抜け、過度な固定を修正する。CIや自己申告だけでは裏付けられない結果を、合格の証拠にしない。
7. 実行環境、データ、権限、外部依存を確認し、条件を実行者が確かめられるか点検する。判断を変える不足だけを質問し、資料や試行で調べられることはその方法へ回す。確認待ちがあれば依存する条件を明示し、独立して進められる範囲は残す。解消できない重要事項を曖昧な条件や合格へ置き換えない。
8. [完了条件の点検と調査根拠](references/completion-review.md)から関係する観点を読み、条件を仕上げる。合否は必須条件ごとに判定し、未実施、証拠不足、確認待ちを成功に数えない。結果に合わせた条件の削除・閾値の緩和・試験の無効化を認めず、正当な変更は既存の権限と決定手順に従って理由と影響を記録する。

## 返すもの

依頼の粒度に応じた短い一覧や表で、目的、範囲と完了段階、基準資料、条件と根拠、確認方法と証拠、未決事項を返す。既存の記録先が指定されていれば更新し、なければ会話内に示す。項目の最小形は次とし、共通する情報はまとめる。

`ID / 必須か参考か / 適用条件・操作 → 期待結果 / 根拠 / 判定方法・証拠`

goalへ渡す場合は、コピーできる一つの文章またはコードブロックも作る。対象と終了段階、必須条件、検証と証拠の提示、守る制約を含める。長い条件は版を特定できる記録のIDへ参照し、実行者が読める場所と未達条件の扱いを本文に残す。参考目標を必須条件へ紛れ込ませない。

ホストが指定されていれば、現在の公式資料で文字数、評価器が見られる情報、権限、停止の仕様を確認して合わせる。未指定ならプロバイダー共通の条件本文を返し、コマンド名や形式を仮定しない。会話だけを読む判定者には、実行した確認、観測結果、対象の版と証拠の場所を会話にも示すよう書く。

予算・期限などの終了制限が指定されていれば、達成判定と分けて引き継ぐ。制限による終了や外部の確認待ちは未完了として扱う。goalへ渡す文章を作る依頼だけでgoalを開始したり、開発、Issue更新や公開まで実行したりしない。

## 作成の完了

重要な要求に対応する必要十分な条件があり、別の判定者が同じ証拠から合否を判断でき、実行と確認に必要な前提がそろえば実行へ渡せる。既存の合意・制約・委任の範囲で条件が確定している場合は、追加承認を一律に要求しない。

実装結果や合否を変える重大な未決事項が残る場合は、goal用の文章も下書きと明記し、条件と次の確認を返す。独立して実行できる範囲の条件と、全体の条件を区別する。外部確認が完了に必要なら、その段階を含む全体の達成条件から黙って除外しない。条件の作成が済んだこと、実装が済んだこと、結果を検証したことを別々に扱う。
